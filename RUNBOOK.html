MySQL HA: полевой справочник

Безопасная диагностика и восстановление для MySQL 8.4, GTID asynchronous replication, Percona Orchestrator Raft и Keepalived VIP. Ищите по симптому. Сначала собирайте состояние, затем меняйте только то, что точно поняли.

MySQL 8.4.12Orchestrator 3.2.6 · три Raft-узлаVIP 10.100.0.5:3306Клиенты 10.100.0.0/1602.10.2026

Начать здесь: пять минут до диагноза

1 · собрать

Не перезапускайте все подряд. Выполните read-only healthcheck и сохраните результат.

2 · определить primary

Сверьте MySQL role и Orchestrator. Не делайте вывод по имени db01 или прошлой закладке.

3 · выбрать ветку

Разделите сеть/VIP, MySQL, авторизацию, репликацию, Orchestrator или приложение.

Стоп перед «починкой». Не удаляйте /srv/mysql/data, не используйте docker compose down -v, RESET REPLICA, RESET MASTER, ручной read_only=OFF или bootstrap на существующем кластере. Если неясно, сколько узлов writable и где самый полный GTID, остановитесь и оставьте узлы read-only.

SSH, sudo и Ansible Vault - разные пароли/ключи. Не присылайте пароль, Vault-файл, содержимое secret mount или полный config с секретами. Ранее пароли уже попадали в переписку: после стабилизации смените их и обновите Vault/узлы согласованно.

Порты: MySQL 3306/tcp; Orchestrator API 3000/tcp; Raft 10008/tcp; VRRP protocol 112. MySQL X 33060 loopback-only. Данные: /srv/mysql/data; конфиг/логи/secrets под /srv/mysql; Orchestrator state: /srv/orchestrator/data.

Как работает VIP: Keepalived требует здоровый локальный MySQL, локальный writable статус и свежий взгляд Orchestrator, где именно этот узел - единственный writable root. Это fail-closed проверка, но не аппаратное fencing старого primary при сетевой партиции.

Штатная проверка

Запустите с контроллера в каталоге репозитория. Команда предназначена для чтения состояния.

ansible-playbook playbooks/healthcheck.yml \
  --ask-vault-pass --ask-become-pass

Ожидается: все три MySQL контейнера healthy; ровно один узел read_only=0 super_read_only=0; два других 1/1; у реплик оба потока ON и источник совпадает с текущим primary; Orchestrator видит один свежий root и все узлы; VIP-проба попадает в этот root.

На DB-узле: контейнер
sudo docker compose -f /srv/mysql/docker-compose.yml ps
sudo docker inspect --format 'status={{.State.Status}} health={{.State.Health.Status}} restarts={{.RestartCount}}' mysql
На DB-узле: MySQL и replication
sudo docker exec mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot -e "SELECT @@server_id,@@read_only,@@super_read_only,@@global.gtid_executed; SHOW REPLICA STATUS\G"'
Orchestrator и VIP
sudo docker compose -f /srv/orchestrator/docker-compose.yml ps
sudo docker logs --since 15m --tail 200 orchestrator
sudo systemctl status keepalived --no-pager
ip -brief address

Сверяйте роли из нескольких источников. При расхождении не продвигайте узел вручную.

Диагностика по симптому

Откройте нужную карточку или используйте поиск сверху.

Клиент не подключается к VIP: timeout / connection refused

Проверка с клиентской машины

nc -vz -w3 10.100.0.5 3306
ip route get 10.100.0.5

Timeout обычно указывает на маршрут, firewall или отсутствующий VIP. Refused обычно означает, что узел доступен, но listener не принимает соединение. Сверьте контейнер MySQL, Orchestrator, Keepalived и VIP на всех трех узлах. Если единственный root подтвержден, но VIP отсутствует - изучите Keepalived и его health script. Не добавляйте VIP вручную, если Orchestrator недоступен или роли спорные.

Workbench: Unable to connect to 10.100.0.5:3306

Сначала проверьте TCP командой выше. Если TCP недоступен - это не пароль: ищите VIP, сеть, firewall, MySQL listener. Если TCP проходит, но MySQL возвращает 1045 - логин/пароль или host match. 1044 означает, что пользователя распознали, но ему не хватает прав на schema. 1290 super-read-only означает replica или fenced node. Root предназначен для локального администрирования; подключайте приложения через VIP под отдельным аккаунтом.

MySQL unhealthy, restarting или не стартует

Соберите первичные ошибки

sudo docker compose -f /srv/mysql/docker-compose.yml ps -a
sudo docker inspect --format 'status={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} health={{.State.Health.Status}}{{range .State.Health.Log}}{{printf "\nprobe exit=%d: %s" .ExitCode .Output}}{{end}}' mysql
sudo docker logs --since 15m --tail 160 mysql
sudo tail -n 120 /srv/mysql/logs/error.log
df -h / /srv
free -h

Ищите самую первую ERROR, а не последующие ошибки о таблицах mysql.*. Проверьте bind mounts, права, конфиг, свободный диск, память и secret mount. Не печатайте в общий чат Docker environment, secrets, Vault или весь Orchestrator config.

При сообщении об уже занятом socket lock сначала проверьте, что контейнер остановлен и процесса mysqld действительно нет. Удалять можно лишь подтвержденные устаревшие конкретные socket/pid/lock-файлы внутри /srv/mysql/run. Не удаляйте весь каталог, тем более datadir.

Один сервер выключен, но сервис еще доступен

Проверьте текущий primary, оба оставшихся MySQL и количество живых Orchestrator Raft members. Кворум трех узлов сохраняется при двух доступных участниках. Если выключен replica, запись может продолжаться на primary. Не выключайте следующий узел до стабилизации и проверки отставшей реплики. SSH timeout не доказывает, что прежний primary обесточен - нужна проверка через консоль гипервизора/out-of-band.

Orchestrator API пустой/недоступен или Raft потерял кворум

Сверьте контейнеры Orchestrator на трех узлах, TCP 10008 между узлами, TCP 3000, время, topology credentials и логи. Без большинства Raft участников не запускайте bootstrap и не создавайте новую topology поверх существующей. VIP специально может исчезнуть, если свежий единственный root не подтвержден. Восстановите связность и кворум, затем повторите healthcheck.

Реплика отстала, IO/SQL thread не запущен

Сохраните SHOW REPLICA STATUS\G, Last_IO_Error, Last_SQL_Error, Retrieved_Gtid_Set, Executed_Gtid_Set и GTID primary. Проверьте сеть, credentials, binlog доступность и Orchestrator. Не выполняйте RESET REPLICA, clone, CHANGE REPLICATION SOURCE и не удаляйте relay/binlog файлы наугад. Без доказанного GTID subset и необходимых binlogs автоматический rejoin должен остановиться.

SSH перестал работать после переустановки ОС

На контроллере удалите fingerprint только нужного адреса: ssh-keygen -R 10.100.0.1. Подключитесь вручную, сверьте fingerprint по доверенному каналу, затем принимайте. Проверьте пользователя и ключ: ansible db01 -m ping. Не отключайте глобально проверку host key.

Primary отказал: порядок действий

Асинхронная репликация не гарантирует нулевую потерю подтвержденных записей. Последние транзакции могли не попасть на replica. TCP-сессии клиентов оборвутся, приложению нужно переподключиться. Короткая пауза и временно отсутствующий VIP во время promotion нормальны.
  1. Не возвращайте прежний primary writable. Если отказал VM, оставьте ее выключенной до выбора нового writer. Если остановлен только контейнер, не снимайте read-only вручную.
  2. Соберите состояние survivors: MySQL роли, source, GTID, оба replication thread; healthcheck и Orchestrator recovery audit.
  3. Убедитесь, что recovery одно и успешно: один successor, только один writable root; второй выживший узел стал его replica.
  4. Проверьте VIP: он только на новом root; с клиента проверьте TCP, затем соединение и тестовую запись через разрешенный app user.
  5. Верните отказавший узел после стабилизации: он должен остаться read-only, безопасно rejoin-нуться текущим primary и догнаться по GTID.
ansible-playbook playbooks/healthcheck.yml \
  --ask-vault-pass --ask-become-pass
ansible-playbook playbooks/recovery.yml \
  --ask-vault-pass --ask-become-pass

playbooks/recovery.yml только читает состояние; он не выполняет promotion или reparent. Если автоматический promotion не произошел, не отправляйте Orchestrator recovery API или SET GLOBAL read_only=OFF без подтвержденного плана fencing и GTID.

Окно теста: остановка контейнера проверяет отказ процесса, но не отказ VM, питания, сети или storage. Тестируйте один отказ за раз и не выключайте следующий сервер до полного восстановления.

Узел вернулся после отказа

Контейнер MySQL настроен с restart unless-stopped. На узлах установлен timer mysql-safe-rejoin.timer. Скрипт безопасно присоединяет read-only реплику к единственному свежему writer, не выполняя RESET и clone.

После перезапуска самого primary MySQL намеренно стартует read-only. Таймер восстановит запись только если все три Orchestrator API показывают одну и ту же полную свежую топологию: этот сервер - единственный корень, две реплики read-only и прямо подключены к нему, SQL applier работает, GTID не расходятся и GTID каждой реплики входят в набор корня. IO-поток может временно быть CONNECTING после рестарта source; это само по себе не запрещает безопасное возобновление. При неясности таймер не снимает read-only, а VIP остается снятым. Чтобы заблокировать такое автоматическое возобновление на время планового обслуживания, заранее создайте на корне marker /srv/mysql/.block-auto-primary-resume; порядок снятия marker после обслуживания должен быть согласован.

sudo systemctl status mysql-safe-rejoin.timer --no-pager
sudo systemctl list-timers --all | grep mysql-safe-rejoin
sudo journalctl -u mysql-safe-rejoin.service --since '-30 min' --no-pager
sudo docker inspect --format 'status={{.State.Status}} health={{.State.Health.Status}}' mysql

На вернувшемся узле подтвердите read_only=1 и super_read_only=1, правильный source и оба потока ON. Дождитесь снижения lag и появления узла под текущим primary в Orchestrator. Не возвращайте старую роль принудительно.

Все узлы read-only, detached или разные primary

Аварийная неоднозначность. Не включайте запись ни на одном узле, не переносите VIP вручную и не bootstrap-ьте topology заново. Новая запись в двух местах превратит сбой в split brain.
  1. Ограничьте клиентскую запись при подозрении на нескольких writers. Сохраните логи и состояние, не уничтожая данные.
  2. На всех узлах сравните read_only, super_read_only, source, replication threads, gtid_executed, gtid_purged и binlog доступность; проверьте последнее наблюдение Orchestrator.
  3. GTID superset сам по себе недостаточен. Убедитесь, что недостающие транзакции доступны, другой узел не содержит уникальных подтвержденных транзакций и старые writers изолированы.
  4. Сделайте проверенную копию/backup перед ручным действием. Назначьте единственного победителя и подтвердите fencing.
  5. Остановитесь для ручного change-reviewed восстановления, если хоть один пункт не доказан.

playbooks/recover_replication.yml - узкая процедура для случая, где все узлы уже detached и fenced read-only. Она проверяет, что replicas являются GTID subset выбранного mysql_primary_host и необходимые транзакции доступны в его binlogs. Это не универсальная команда восстановления, не запускайте на штатном кластере. Имя db01 в переменной может быть устаревшим относительно текущего primary; перед любой процедурой надо прочитать playbook и заново доказать выбор кандидата.

ansible-playbook playbooks/recovery.yml \
  --ask-vault-pass --ask-become-pass

Клиент, аккаунты и права

Для приложения используйте host 10.100.0.5, port 3306 и отдельный app account. Root ограничен локальным администрированием. Типовые ошибки: 2002/timeout - endpoint/listener/route; 1045 - пароль/host match; 1044 - нет grants на schema; 1290 - узел read-only.

Аккаунт furzik на этом кластере уже создавался вручную, поэтому не запускайте повторный CREATE USER из старых инструкций. После подключения под ним проверьте, какая запись MySQL выбрана и какие права она имеет:

SELECT CURRENT_USER();
SHOW GRANTS;

Если подключение отвергнуто из-за адреса клиента, администратор на подтверждённом primary проверяет существующие записи учётной записи:

SELECT User, Host FROM mysql.user WHERE User = 'furzik';

Согласно последнему изменению, для furzik разрешена сеть 10.100.0.0/255.255.0.0; проверяйте фактическое состояние перед изменением прав. Эта учётная запись не описана в Ansible и не появится автоматически при развёртывании с нуля. Права на создание схем и другие DDL-действия определяются результатом SHOW GRANTS, а не самим фактом успешного подключения.

Добавить нового MySQL-пользователя

Эти команды создают пример пользователя new_app_user с доступом только к существующей базе appdb. Выполняйте их один раз на подтверждённом текущем primary, а не по очереди на всех узлах. Сначала подключитесь к MySQL на этом сервере (не предполагайте, что primary всё ещё db01):

sudo docker exec -it mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot'

В открывшейся SQL-консоли проверьте роль. Продолжайте только если оба значения равны 0:

SELECT @@global.read_only, @@global.super_read_only;

Замените имя new_app_user на нужное. MySQL покажет сгенерированный пароль в результате CREATE USER: сразу сохраните его в менеджере паролей и не отправляйте в переписку. Если такая учётная запись уже существует, команда остановится с ошибкой — не меняйте её пароль вслепую.

CREATE USER 'new_app_user'@'10.100.0.0/255.255.0.0'
  IDENTIFIED BY RANDOM PASSWORD;
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE TEMPORARY TABLES, SHOW VIEW
  ON appdb.* TO 'new_app_user'@'10.100.0.0/255.255.0.0';
SHOW GRANTS FOR 'new_app_user'@'10.100.0.0/255.255.0.0';

С клиента из разрешённой сети проверьте вход через VIP; -p запросит пароль без записи его в командную строку:

mysql -h 10.100.0.5 -P 3306 -u new_app_user -p \
  -e "SELECT CURRENT_USER(), @@server_id, @@read_only;"

Права ограничены базой appdb: пользователь не сможет создать новую базу или управлять другими пользователями. Для новых схем и административных прав нужен отдельный осознанный запрос. Эти ручные учётные записи не описаны в Ansible и при чистом развёртывании не создаются автоматически. FLUSH PRIVILEGES после CREATE USER и GRANT не требуется.

Работа непосредственно в MySQL

Повседневные клиентские запросы выполняйте через VIP 10.100.0.5:3306, а не через адрес конкретной VM. На клиентском компьютере с установленным mysql подключитесь под своей учётной записью; -p запрашивает пароль интерактивно:

mysql -h 10.100.0.5 -P 3306 -u furzik -p

В консоли MySQL проверьте, какая учётная запись применена и куда привёл VIP. @@read_only=0 и @@super_read_only=0 ожидаются для текущего writer; при других значениях не пытайтесь принудительно включать запись.

SELECT CURRENT_USER(), @@server_id, @@read_only, @@super_read_only;
SHOW GRANTS;
SHOW DATABASES;
USE appdb;
SHOW TABLES;
SELECT TABLE_NAME, TABLE_ROWS FROM information_schema.TABLES WHERE TABLE_SCHEMA = 'appdb' LIMIT 20;

TABLE_ROWS для InnoDB является оценкой, а не точным подсчётом. Для чтения конкретных данных сначала выберите реальную таблицу через SHOW TABLES, затем выполняйте ограниченный SELECT ... LIMIT. Изменяющие запросы (INSERT, UPDATE, DELETE, DDL) выполняйте только после проверки нужной базы, условий WHERE, прав и актуального backup; на replica они должны отклоняться. Не повторяйте запрос после timeout вслепую: запись могла успеть зафиксироваться.

Администраторские проверки на DB-узле

Для просмотра состояния каждой ноды подключайтесь к ней по SSH и используйте локальный socket. Это диагностика, а не способ посылать клиентские записи в обход VIP:

sudo docker exec mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot -e "SELECT @@server_id, @@read_only, @@super_read_only, @@global.gtid_executed; SHOW REPLICA STATUS\G"'

На primary SHOW REPLICA STATUS обычно пустой; на replica проверьте source, оба потока и ошибки. Создание аккаунта описано в разделе «Добавить пользователя»; диагностика отказов и разошедшихся GTID - в разделах выше.

Администрирование через Ansible

Все команды ниже выполняются на управляющей машине из каталога проекта /home/furzik/ansible-test, не в SSH-сессии DB-узла. ansible.cfg уже задаёт inventory/production.yml; --ask-become-pass запрашивает sudo-пароль, --ask-vault-pass - пароль Vault. Не добавляйте секреты в параметры -e или историю shell.

Проверить доступ и состав узлов

cd /home/furzik/ansible-test
ansible-inventory --graph
ansible mysql_cluster -m ping

Если SSH-ключ изменился после переустановки VM, вручную сверьте новый host fingerprint по доверенному каналу до повторного bootstrap. Не отключайте проверку SSH host key глобально.

Диагностика и preflight

ansible-playbook playbooks/deploy.yml --tags preflight \
  --ask-vault-pass --ask-become-pass
ansible-playbook playbooks/healthcheck.yml \
  --ask-vault-pass --ask-become-pass
ansible-playbook playbooks/recovery.yml \
  --ask-vault-pass --ask-become-pass

preflight проверяет условия развёртывания и может устанавливать вспомогательный пакет; это не строго read-only команда. healthcheck.yml и recovery.yml собирают состояние, но не выполняют promotion или reparent. В healthcheck часть диагностических задач допускает ошибку, поэтому один лишь код выхода playbook не доказывает, что кластер здоров: прочитайте результаты по всем трём узлам и сверьте роли, GTID, репликацию и VIP.

Не используйте deploy как кнопку восстановления. После failover исходная переменная seed mysql_primary_host может не совпадать с текущим primary. Полный deploy.yml, bootstrap-подтверждение, recover_replication.yml, destroy.yml и изменение Vault запускайте только по отдельной проверенной процедуре. Orchestrator отвечает за автоматическое переключение, Ansible - за конфигурацию и диагностику.

Агент нагрузки и Dashboard

В настройках target должен быть VIP 10.100.0.5:3306, а не закрепленный DB-узел. При ошибках на графике сначала проверьте VIP и MySQL, затем backend. Во время failover возможны ошибки и рост latency; после backend restart workload session может требовать нового запуска из UI.

cd /home/furzik/agent-bd
sudo docker compose ps
sudo docker compose logs --since 15m --tail 200 backend
curl -fsS http://127.0.0.1:8000/health
curl -fsS http://127.0.0.1:8000/ready

/health подтверждает процесс, /ready также проверяет backend readiness/SQLite. Не запускайте несколько backend workers на одной SQLite. Timeout не доказывает, что INSERT не попал в БД: не повторяйте такую операцию автоматически, сначала проверьте данные. Агент не должен использовать MySQL root или менять grants.

Различайте сбои: если TCP и отдельная безопасная SQL-проверка через VIP успешны, а Dashboard показывает ошибки - смотрите backend logs и отчет конкретной сессии. Reconnect пула не означает автоматическое продолжение остановленной сессии нагрузки.

Плановое обслуживание и тест отказа

Один узел за раз

  1. Согласуйте окно; при необходимости остановите тестовую нагрузку. Установите текущий primary и убедитесь, что оставшиеся узлы здоровы.
  2. При обслуживании replica остановите только ее сервис; проверьте продолжение работы writer. Не трогайте следующий узел до восстановления replica.
  3. Для обслуживания primary не используйте случайный stop как switchover: он инициирует аварийный failover. Нужна поддерживаемая и отдельно проверенная процедура.
  4. После запуска дождитесь healthy, безопасного rejoin и catch-up; проверьте read-only роль. Только потом планируйте следующий узел.

Fault injection

Только на тестовых VM с наблюдателем, сохраненными GTID и доступом к консоли. Один отказ за раз. После него подтвердите единственного writer, единственный VIP, reparent второй replica, восстановление упавшего узла. Выключение контейнера не доказывает поведение при потере VM, сети, питания или storage.

Bootstrap не для повседневного deploy. Флаг YES_INITIALIZE_ASYNC_REPLICATION только для разовой инициализации пустых datadir. playbooks/update.yml сейчас собирает диагностику и не выполняет rolling upgrade. Не передавайте destroy confirmations ради восстановления.

Бэкап и обновления

Реплика не является backup: ошибочный UPDATE/DELETE также размножится. Настройте резервирование на независимое хранилище и проверьте restore. Не копируйте живой datadir как backup. Обновления сначала репетируйте на тестовой копии и проверяйте совместимость версий.

Расширить корневой диск VM

На db01/db03 обнаружена схема /dev/sda → /dev/sda3 → ubuntu-vg/ubuntu-lv → ext4 /. Текущий 32-ГБ диск уже распределён полностью: сначала увеличьте ёмкость виртуального диска каждой VM в гипервизоре и сохраните проверенный backup/snapshot. Playbook не меняет размер диска в гипервизоре, не удаляет MySQL-данные и откажется работать при иной схеме разделов. Если db02 недоступен, не включайте его в запуск.

На каждой VM перед запуском убедитесь, что lsblk видит новый размер /dev/sda:

lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS /dev/sda
df -h /
sudo vgs

С управляющей машины запустите новый playbook строго по одному узлу. Пример для db01; после проверки результата замените db01 на db03, затем на db02, когда он станет доступен:

cd /home/furzik/ansible-test
ansible-playbook playbooks/expand_root_disk.yml --limit db01 \
  --ask-become-pass -e confirm_expand_root_lvm=YES_EXPAND_ROOT_LVM

Если Ansible недоступен, после проверки той же схемы диска и увеличения /dev/sda в гипервизоре выполните на одной VM вручную:

sudo env TMPDIR=/run growpart --fudge 0 /dev/sda 3
sudo pvresize /dev/sda3
sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
df -h /

Playbook выполняет эти действия с проверками схемы диска и не требует места в /tmp для Ansible-модулей. Повторный запуск допустим: уже расширенные слои останутся без изменений. Если раздел не вырос или после запуска df всё ещё показывает нулевое свободное место, playbook завершится ошибкой; не удаляйте binlog вручную.

После расширения проверьте состояние MySQL, Orchestrator и VIP через штатную проверку. Добавление места само по себе не восстановит недоступный db02 и Raft-кворум. Планируйте запас ёмкости и срок хранения binlog отдельно: увеличение диска устраняет текущую нехватку места, но не причину постоянного роста.

Логи и данные для разбора

Каждый DB-узел

MySQL container health/restarts, первые ошибки в docker/error log, SHOW REPLICA STATUS, GTID, timer journal, Keepalived и наличие VIP.

Orchestrator

Логи всех доступных members, Raft quorum, topology, freshness узлов, recovery audit и failure analysis. Credentials не публикуйте.

Клиент

Время/timezone, адрес и порт, nc результат, точный MySQL error code/message без пароля, сетевой путь.

Сохранить до исправления

GTID каждого узла, writable/read-only роли, source, ошибки IO/SQL и полное событие recovery с временными метками.

ansible-playbook playbooks/healthcheck.yml \
  --ask-vault-pass --ask-become-pass
ansible-playbook playbooks/recovery.yml \
  --ask-vault-pass --ask-become-pass

Не присылайте vault.yml, содержимое secrets, пароль в аргументах команды или неотредактированный config. Healthcheck может включать GTID и внутренние адреса - учитывайте политику публикации.

Что автоматизировано и границы обещаний

Ожидаемая автоматика

Orchestrator следит за source/replica и настроен на автоматический promotion. Keepalived переносит VIP при подтвержденном совпадении role. mysql-safe-rejoin возвращает GTID-совместимую read-only replica.

Не гарантируется

Нулевой RPO при async replication; мгновенный failover; сохранение клиентских TCP-сессий; безопасное автоматическое разрешение любой сетевой партиции без external fencing; починка divergent GTID или поврежденных данных.

Проверено в истории проекта

Тест отказа одного MySQL container: Orchestrator выбрал db03, db02 перешел под него, VIP восстановился, db01 вернулся read-only и rejoin-нулся. Это service-level тест, не длительный soak и не выключение VM/сети.

Нужно тестировать отдельно

Длительная нагрузка, полное выключение VM primary, потеря двух Raft members, L2/VRRP partition, одновременные отказы и восстановление из backup.

Для гарантии сохранения каждой подтвержденной записи при отказе одного узла async replication недостаточно. Нужны отдельный выбор quorum/semi-sync архитектуры, fencing и клиентских retry-политик. Одна настройка не превращает систему в zero-RPO.

В конце: снять блокировку повторного failover

Orchestrator временно блокирует повторное автоматическое восстановление после предыдущего failover, чтобы кластер не переключался по кругу. В этой конфигурации RecoveryPeriodBlockSeconds равен 30 секундам; обычно блокировка истекает сама. Антифлап-защиту глобально не отключайте: во время сетевой партиции или нестабильности это повышает риск двух primary и конфликтующих записей.

  1. Выполните playbooks/healthcheck.yml, изучите UI Audit → Recoveries, логи Orchestrator, роли MySQL и GTID. Убедитесь, что другое восстановление сейчас не выполняется.
  2. Если primary есть, он должен быть ровно один. Если primary нет, кандидаты должны быть fenced/read-only, а их GTID - проверены на совместимость. Если старый primary доступен для записи, GTID расходятся или роль неясна - не подтверждайте восстановление и не включайте запись вручную.
  3. В Audit → Recoveries выберите событие для production-mysql и подтвердите (acknowledge) именно это восстановление/кластер. Не выбирайте Force failover.
  4. Дождитесь нового цикла анализа и снова выполните healthcheck. Проверьте один writable root, потоки репликации на репликах и подключение через VIP. Ack снимает блок ожидания, но сам по себе не повышает узел.

CLI выполняйте на текущем лидере Raft; пароль вводите только в скрытый prompt, не вставляйте его в командную строку и не используйте set -x:

read -rp 'Orchestrator API user: ' ORC_USER
read -rsp 'Orchestrator API password: ' ORC_PASS; echo
sudo docker run --rm --network host \
  --entrypoint orchestrator-client \
  -e ORCHESTRATOR_API=http://127.0.0.1:3000/api \
  -e "ORC_AUTH=${ORC_USER}:${ORC_PASS}" \
  percona/percona-orchestrator:3.2.6 \
  -c ack-cluster-recoveries \
  -alias production-mysql \
  -reason "validated topology and cleared recovery block"
unset ORC_USER ORC_PASS

Не применяйте ack-all-recoveries - он снимает блокировки во всех кластерах. Не подменяйте ack командами recover или force-master-failover без отдельного доказательства безопасности кандидата.

Возврат ноды с GTID после failover

Определите текущий primary по Orchestrator и подтвердите, что это единственный writable-узел. На нём скопируйте полный GTID-набор:

sudo docker exec mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot -NBe "SELECT @@global.gtid_executed"'

На возвращаемой ноде откройте SQL-консоль, вставьте GTID-набор primary и сравните направления расхождения:

sudo docker exec -it mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot'
SET @primary_gtid = 'PASTE_PRIMARY_GTID_SET';
SELECT @@server_id, @@global.read_only, @@global.super_read_only;
SELECT GTID_SUBTRACT(@@global.gtid_executed, @primary_gtid) AS extra_on_this_node,
       GTID_SUBTRACT(@primary_gtid, @@global.gtid_executed) AS missing_on_this_node;

Если extra_on_this_node пустой и нода остаётся read-only (1/1), выйдите из SQL-консоли и запустите установленный контроллер rejoin:

sudo systemctl start mysql-safe-rejoin.service
sudo journalctl -u mysql-safe-rejoin.service -n 30 --no-pager
sudo docker exec mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot -e "SHOW REPLICA STATUS\G"'

Ожидайте attached to current primary via GTID auto-position, already replicating from the current primary или started existing replica channel. В статусе реплики проверьте адрес текущего primary, оба потока Yes и отсутствие ошибок. Затем повторите playbooks/healthcheck.yml.

Если extra_on_this_node не пустой: у ноды есть транзакции, отсутствующие на primary. Сохраните GTID, binlog и backup, затем разберите изменения. Данные нужно согласовать вручную либо сохранить старый datadir отдельно и клонировать ноду из актуального primary. Не очищайте и не подделывайте GTID для обхода проверки: это может скрыть потерянные записи. Если лишних GTID нет, но primary уже удалил нужные ноде binlog, тоже потребуется актуальный backup/клонирование.

Для разобранного инцидента 09.10.2026 предусмотрен отдельный playbooks/reclone_db01_from_db03.yml. Он откажется работать, если текущая топология или лишний GTID db01 уже отличаются от проверенных. После явного разрешения владельца данных playbook заменяет datadir db01 копией db03 и присоединяет db01 read-only. Изолированная транзакция db01 при этом теряется, если её нет в отдельной резервной копии. Не используйте этот playbook как универсальную команду для следующего сбоя.

ansible-playbook playbooks/reclone_db01_from_db03.yml --ask-vault-pass --ask-become-pass -e confirm_reclone_db01_from_db03=YES_DISCARD_DB01_EXTRA_GTID
ansible-playbook playbooks/healthcheck.yml --ask-vault-pass --ask-become-pass

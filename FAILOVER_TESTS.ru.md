# Приёмочные испытания MySQL Replication + Orchestrator

Проводите испытания только на тестовых или одноразовых ВМ без пользовательских данных. До и после каждого испытания фиксируйте наборы выполненных и полученных GTID. На каждом шаге проверяйте, что запись разрешена ровно на одном узле и что VIP принадлежит именно ему. Эти испытания необходимо пройти, прежде чем считать топологию готовой к эксплуатации.

## Исходное состояние

1. Запустите `playbooks/healthcheck.yml`; все три контейнера MySQL должны быть в состоянии `healthy`.
2. На каждом узле проверьте `SHOW REPLICA STATUS\G`, `@@global.read_only` и `@@global.super_read_only`. У primary нет источника репликации и разрешена запись. Обе реплики должны ссылаться на primary, иметь запущенные потоки репликации и работать только на чтение.
3. Запросите API Orchestrator `/api/cluster/alias/production-mysql`. Ответ должен содержать все ожидаемые узлы, один текущий корневой узел и свежие корректные результаты проверок.
4. Убедитесь, что VIP находится только на доступном для записи корневом узле и принимает тестовую запись через порт 3306. Проверьте, что узлы только для чтения отклоняют запись.

## Отказ процесса primary

1. Зафиксируйте GTID, затем остановите только контейнер MySQL на primary.
2. Убедитесь, что Orchestrator обнаружил отказ и повысил только одну подходящую реплику. Проверьте, что другая реплика переключилась на новый источник.
3. Убедитесь, что Keepalived снял VIP с отказавшего сервера и назначил его только новому доступному для записи корневому узлу. Запишите строку через VIP:3306 и проверьте её на обеих репликах.
4. Перезапустите прежний primary. Пока он отстаёт или работает только на чтение, он не должен получать VIP. Прежде чем рассматривать управляемый возврат роли primary, убедитесь, что узел присоединился как реплика к новому primary и догнал его.

## Отказ Orchestrator/Raft

1. Остановите один экземпляр Orchestrator. При двух оставшихся из трёх наблюдайте за работой API и VIP; одновременно должно существовать не более одного VIP и одного доступного для записи primary.
2. Остановите второй экземпляр. Там, где нельзя подтвердить текущую топологию, проверка Keepalived должна запрещать выдачу VIP. Проверьте и задокументируйте поведение существующего пишущего MySQL и клиентского адреса; не запускайте принудительное повторное повышение узла.
3. Восстановите экземпляры Orchestrator и проверьте, что состояние Raft согласовалось, а обнаруженная топология не потеряна.

## Сетевое разделение и проверка защиты от split-brain

В изолированной тестовой сети заблокируйте репликацию MySQL между прежним primary и обеими репликами, оставив прежний primary доступным клиентам. Отдельно заблокируйте соединения Orchestrator/Raft. Проверьте, остаётся ли прежний primary доступным для записи, повышает ли Orchestrator другой узел и может ли Keepalived открыть клиентам доступ к нескольким пишущим либо устаревшим узлам. В текущей системе нет внешнего STONITH или отключения питания отказавшего узла. Если при таком испытании возможны два доступных для записи узла, система не проходит приёмку: не используйте её для рабочих записей, пока не добавите fencing либо равноценную архитектуру с безопасным кворумом и не повторите испытания.

## Проверка реплики и восстановления

1. Остановите одну реплику. Записи на primary должны продолжаться, а другая реплика — оставаться актуальной.
2. Запустите остановленную реплику и проверьте, что она догнала primary через автоматическое позиционирование по GTID.
3. Отдельно проверьте восстановление из проверенной резервной копии. Никогда не выполняйте `RESET REPLICA`, клонирование, удаление данных или переключение источника на узле с неясным состоянием GTID без резервной копии и явной проверки оператором.

## В конце: проверить и снять блокировку повторного failover

Orchestrator временно блокирует повторное автоматическое восстановление после предыдущего failover, чтобы кластер не переключался по кругу. В конфигурации этого проекта `RecoveryPeriodBlockSeconds` установлен в 30 секунд. Обычно блокировка истекает сама. Не отключайте антифлап-защиту: при сетевой партиции или нестабильных узлах повторное повышение может привести к двум primary и конфликтующим записям.

Если в UI написано `DeadMaster ... is blocked due to a previous recovery`:

1. Сначала выполните `playbooks/healthcheck.yml` и изучите топологию, логи Orchestrator, роли MySQL и GTID. Убедитесь, что нет уже выполняющегося восстановления. Если есть primary, он должен быть ровно один; если primary нет, все кандидаты должны быть fenced/read-only и проверены на GTID-совместимость. Если старый primary доступен для записи, GTID расходятся или роль узла неясна - НЕ подтверждайте восстановление и не включайте запись вручную.
2. В Orchestrator откройте раздел аудита восстановлений (Audit -> Recoveries), найдите событие кластера `production-mysql`, проверьте детали, затем используйте действие подтверждения/acknowledge для этого кластера. Не выбирайте `force failover`.
3. После подтверждения дождитесь нового цикла анализа и повторите штатный healthcheck. Убедитесь, что Orchestrator видит один root, реплики подключены и имеют запущенные потоки, а запрос через VIP попадает на единственный writable primary. Ack только снимает блок ожидания; это не повышает узел самостоятельно.

CLI-вариант выполняется на текущем лидере Orchestrator (Raft), не на случайном DB-узле. Команда запросит HTTP API логин и пароль скрытым вводом; не включайте `set -x` и не вставляйте пароль непосредственно в строку команды:

```bash
read -rp 'Orchestrator API user: ' ORC_USER
read -rsp 'Orchestrator API password: ' ORC_PASS; echo
sudo docker run --rm --network host \
  --entrypoint orchestrator-client \
  -e ORCHESTRATOR_API=http://127.0.0.1:3000/api \
  -e "ORC_AUTH=${ORC_USER}:${ORC_PASS}" \
  percona/percona-orchestrator:3.2.6 \
  -c ack-cluster-recoveries \
  -alias production-mysql \
  -reason "validated topology and cleared recovery block"
unset ORC_USER ORC_PASS
```

Если CLI не подключается к API, используйте UI либо задайте клиенту адрес API лидера и HTTP Basic Auth способом, принятым в вашей среде. После команды обязательно проверьте UI/API `blocked-recoveries` и выполните healthcheck. Не используйте `ack-all-recoveries`: он снимает блокировки не только этого кластера. Не применяйте `recover` или `force-master-failover` как замену ack без отдельной проверки кандидата и явного решения об отказе.

## Возврат отсоединившейся ноды с GTID

Все команды ниже выполняются на указанном DB-сервере. Сначала определите **текущий** primary по Orchestrator и проверьте, что он единственный writable-узел. Не считайте db01 постоянным primary.

На текущем primary получите его GTID-набор:

```bash
sudo docker exec mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot -NBe "SELECT @@global.gtid_executed"'
```

На возвращаемой ноде откройте локальную SQL-консоль и подставьте скопированный набор вместо `PASTE_PRIMARY_GTID_SET`:

```bash
sudo docker exec -it mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot'
```

```sql
SET @primary_gtid = 'PASTE_PRIMARY_GTID_SET';
SELECT @@server_id, @@global.read_only, @@global.super_read_only;
SELECT GTID_SUBTRACT(@@global.gtid_executed, @primary_gtid) AS extra_on_this_node,
       GTID_SUBTRACT(@primary_gtid, @@global.gtid_executed) AS missing_on_this_node;
```

Если `extra_on_this_node` пустой, а локальный узел полностью read-only (`1/1`), закройте SQL-консоль и запустите уже установленный контроллер безопасного присоединения:

```bash
sudo systemctl start mysql-safe-rejoin.service
sudo journalctl -u mysql-safe-rejoin.service -n 30 --no-pager
sudo docker exec mysql sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql_root_password)" mysql --protocol=socket --socket=/var/run/mysqld/mysqld.sock -uroot -e "SHOW REPLICA STATUS\G"'
```

В журнале должно появиться сообщение `attached to current primary via GTID auto-position` или `already replicating from the current primary`. В `SHOW REPLICA STATUS` проверьте адрес текущего primary, `Replica_IO_Running: Yes`, `Replica_SQL_Running: Yes` и отсутствие ошибок. Затем повторите `playbooks/healthcheck.yml`. Если источник уже указан правильно, но потоки остановлены, контроллер может выдать `started existing replica channel`.

Если `extra_on_this_node` **не пустой**, автоматический rejoin намеренно остановится: на этой ноде есть транзакции, которых нет на primary. Сохраните вывод GTID-проверки, binlog и резервную копию ноды; установите, какие данные изменили эти транзакции, и решите, как устранить конфликт. Варианты — вручную перенести данные с проверкой конфликтов либо сохранить старый datadir отдельно и заново клонировать ноду из актуального primary. Для этого случая нет безопасной универсальной команды `CHANGE REPLICATION SOURCE TO`: нельзя просто очистить или подделать GTID, а `RESET MASTER`/`RESET REPLICA` может скрыть потерю подтверждённых записей. Если `extra_on_this_node` пустой, но primary уже удалил нужные `missing_on_this_node` транзакции из binlog, потребуется восстановление из актуального backup/клонирование.

Для инцидента 09.10.2026 создан отдельный `playbooks/reclone_db01_from_db03.yml`: он проверяет, что db03 всё ещё primary и единственный владелец VIP, db01 отсоединена и имеет **ровно** ранее разобранный лишний GTID, а затем заменяет данные db01 MySQL Clone и присоединяет её read-only. Эта операция **безвозвратно отбрасывает** изолированную транзакцию db01, если её нет в отдельной резервной копии. Владелец данных явно разрешил это для данного инцидента. Playbook не является общей процедурой на будущее: для другого сбоя сначала повторите анализ GTID и создайте новую проверку точной топологии.

```bash
ansible-playbook playbooks/reclone_db01_from_db03.yml --ask-vault-pass --ask-become-pass -e confirm_reclone_db01_from_db03=YES_DISCARD_DB01_EXTRA_GTID
ansible-playbook playbooks/healthcheck.yml --ask-vault-pass --ask-become-pass
```
